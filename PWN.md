# PWN: от устройства процесса до продвинутого анализа бинарей

**Редакция:** 2.0 · **Дата:** 25 сентября 2026 г.  
**Основная платформа:** Linux, ELF, x86-64, System V ABI, glibc.  
**Формат:** объяснения → локальные лаборатории → ожидаемый результат → ограничения.

Это руководство помогает понимать PWN-задачи, исследовать бинарные программы и проверять свои выводы экспериментом. Вместо универсального «найди offset и отправь payload» здесь используется последовательность:

> **Зафиксировать среду → понять контракт программы → изучить исполнение и память → проверить гипотезу → сохранить доказательства.**

Практическая часть посвящена собственным локальным программам, отладке, проверке границ, времени жизни объектов и механизмам защиты. Продвинутые техники эксплуатации объясняются на уровне устройства, терминологии и ограничений; готовых exploit-цепочек, перебора защит и автоматического взаимодействия с внешними целями здесь нет.

Все исходники лабораторий находятся в этом файле. Для обязательной части не нужны сторонние challenge-бинарники, Docker, платные инструменты, pwndbg или pwntools.

## 1. Как пользоваться руководством

### Сначала — минимальная рабочая модель

Нужно различать четыре уровня:

| Уровень | На какой вопрос отвечает |
|---|---|
| Язык C/C++ | Какие операции допустимы, где границы объекта, кому принадлежит память? |
| ABI и машинный код | Где аргументы, как выполняется вызов, какие регистры сохраняются? |
| ELF и загрузчик | Как код и данные попадают в память, откуда берутся библиотеки? |
| ОС и механизмы защиты | Какие страницы и системные вызовы доступны процессу? |

Ошибка на одном уровне не позволяет автоматически сделать вывод на другом. Например, выход за границу C-массива — ошибка даже тогда, когда обращение попало в отображённую страницу и процесс не завершился.

**Начальный маршрут:** разделы 2–10, лаборатории A–C. Результат — ты умеешь собрать программу, объяснить её ввод и проследить выполнение.

**Следующий уровень:** разделы 11–19. Результат — ты отличаешь ошибку программы от различий загрузчика, allocator, ABI или instrumentation.

**Продвинутый маршрут:** разделы 15–20 вместе с первоисточниками. Результат — ты понимаешь границы применимости техник, а не переносишь старую инструкцию на любой ELF.

### Что считать доказанным

Пример хорошей записи:

> В `frame_demo` из текущей сборки заголовок объявляет 65 байт. Программа завершилась с кодом 2, не вывела ответ в stdout, stderr содержит ошибку формата. Это подтверждает обработку данного невалидного запроса, но не доказывает корректность всех путей выполнения.

Пример плохой записи:

> Здесь Full RELRO, значит задача безопасна / сложная / требует конкретной техники.

**Правило:** у каждого важного вывода должны быть условия, наблюдение и граница применимости.

## 2. Быстрый старт и извлечение лабораторий

### 2.1. Где выполнять команды

Рабочий вариант — отдельная Linux x86-64 VM. Ubuntu 24.04 подходит как целевая среда для приведённых команд; фактически проверенная среда указана в [разделе 26](#verification). На macOS выполняй Linux-лаборатории внутри VM либо на отдельной Linux-машине. Mach-O, Darwin ABI и Linux ELF — не одно и то же.

Не используй рабочий сервер с секретами для запуска неизвестных бинарей. Для такого анализа предпочтительна одноразовая VM без общих каталогов и учётных данных. Контейнер полезен для упаковки user space, но не следует считать его отдельной виртуальной машиной: процессы контейнера используют ядро хоста. См. [документацию Docker по модели безопасности][docker-security].

### 2.2. Зависимости

В Debian/Ubuntu VM:

```bash
sudo apt update
sudo apt install --no-install-recommends \
  build-essential binutils file gdb strace python3 python3-venv
```

Это установка пакетов **в учебной VM**. После подготовки инструментов обязательные лаборатории можно выполнять без сети. Для отката всей среды используй снимок VM; не удаляй наугад системные библиотеки.

Проверка:

```bash
uname -m
gcc --version
python3 --version
readelf --version
gdb --version
```

Для этой редакции лабораторий `uname -m` должен показывать `x86_64`. Фильтр seccomp ниже намеренно ограничен native x86-64, не x32 ABI.

### 2.3. Получить все исходники из этого Markdown

Сохрани документ под именем `PWN.md`. В каталоге с ним выполни:

```bash
python3 - PWN.md <<'PY'
from pathlib import Path
import re
import sys

source = Path(sys.argv[1])
root = Path("pwn-lab")
expected = {
    "Makefile", "src/frame.h", "src/frame.c", "src/frame_main.c",
    "src/abi.c", "src/ownership.c", "src/seccomp_demo.c",
    "tests/test_frame.c", "tests/test_protocol.py",
    "tools/collect.py", "tools/pwn_local.py",
}
try:
    text = source.read_text(encoding="utf-8")
    entries = re.findall(
        r"(?ms)^<!-- lab-file: ([\w./-]+) -->\n```[^\n]*\n(.*?)^```[ \t]*$",
        text,
    )
    names = [name for name, _ in entries]
    if set(names) != expected or len(names) != len(expected):
        raise ValueError("Missing, duplicate or unexpected lab files")
    if root.exists() or root.is_symlink():
        raise FileExistsError("pwn-lab already exists; choose a fresh directory")
    root.mkdir()
    for name, content in entries:
        path = root / name
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(content, encoding="utf-8")
except (OSError, ValueError) as exc:
    raise SystemExit(f"ERROR: {exc}")
print(f"Created {len(entries)} files in {root}")
PY
```

Извлечение создаёт только новый каталог `pwn-lab`, проверяет список имён и не перезаписывает существующий проект. Сборка и запуск на этом шаге ещё не происходят.

### 2.4. Собрать и проверить

```bash
cd pwn-lab
make test
make sanitize
make sandbox-test
python3 tools/collect.py build/frame_demo build/report-01
```

Здесь четыре независимые проверки:

| Команда | Ожидаемый результат |
|---|---|
| `make test` | Тесты парсера проходят; `PASS: 73 protocol cases`; две строки `sum=28`; пример владения завершается штатно |
| `make sanitize` | Те же тесты проходят под ASan/UBSan, без отчётов об ошибках |
| `make sandbox-test` | `PASS: getpid blocked with EPERM` |
| `tools/collect.py ...` | Создан `manifest.json` и текстовые отчёты; цель не запускалась сборщиком |

Ненулевой код завершения — повод прочитать сообщение, а не автоматически повторять тест с отключёнными защитами. У seccomp-демонстрации код 77 означает невозможность выполнить подготовку фильтра в данной среде; это **не пройденный тест**.

Каталоги отчётов не перезаписываются. Для следующего запуска укажи `build/report-02`.

### 2.5. Необязательный pwntools

В этой редакции пример привязан к `pwntools==4.15.0`. Это выбранная версия, а не обещание, что она всегда будет последней. API см. в [официальной документации][pwntools-tubes].

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install 'pwntools==4.15.0'
python -m pip freeze > requirements.lock.txt
python tools/pwn_local.py
```

Ожидаемый результат: `PASS: local pwntools exchange`. Статус фактической проверки этого дополнительного примера см. в [разделе 26](#verification).

Для выхода из virtualenv выполни `deactivate`. Системный Python не изменяется. `pip freeze` сохраняет версии, но сам по себе не фиксирует хеши пакетов и не обеспечивает побитово идентичное окружение.

## 3. Рабочая среда и воспроизводимость

### 3.1. Что сохранять

Для каждого исследуемого случая создай отдельный каталог. Оригинальные файлы не патчь: для эксперимента делай копию с новым именем и новым хешем.

```text
case/
  original/       исходные бинарь, библиотеки, описание
  working/        копии и локальные сборки
  evidence/       логи, входы, результаты, хеши
  notes.md        факты, гипотезы и следующие проверки
```

Минимальный паспорт включает: SHA-256 бинаря, архитектуру, build ID при наличии, ядро, libc и загрузчик, версии инструментов, параметры компиляции, рабочий каталог и точный способ передачи ввода.

Не выгружай в отчёт весь `env`: там могут быть токены и пароли. Сохраняй только относящиеся к эксперименту параметры. Core dump тоже может содержать секреты; это не безобидный технический лог. Формат и ограничения дампов описаны в [core(5)][core].

### 3.2. Три разных вида воспроизводимости

**Функциональная:** одинаковые входы дают одинаковый смысловой результат.

**Средовая:** совпадают значимые версии, настройки и способ запуска.

**Побитовая:** повторная сборка даёт тот же файл и хеш.

Первое не подразумевает второе или третье. Лаборатории ниже рассчитаны на функциональную воспроизводимость; различающиеся адреса при ASLR не считаются ошибкой.

### 3.3. Инструменты и их роли

| Инструмент | Для чего нужен | Чего от него не ждать |
|---|---|---|
| `file`, `readelf`, `objdump` | Статическое описание файла | Доказательства runtime-поведения |
| GDB | Управляемое исполнение и наблюдение состояния | Полного восстановления исходного C |
| pwndbg | Дополнительное представление данных в отладчике | Замены знания ABI и проверки версии |
| `strace` | Наблюдение системных вызовов | Всех обращений к памяти или всех возможных путей |
| ASan/UBSan | Динамические проверки при инструментированной сборке | Доказательства отсутствия всех ошибок |
| pwntools | Байтовый ввод-вывод и вспомогательные операции | Правильной модели протокола «по умолчанию» |

Основной маршрут работает с обычным GDB. Дополнения ставь отдельно, из доверенного источника, с фиксацией версии. Не начинай диагностику с глобального отключения ограничений `ptrace`, ASLR или загрузки произвольных GDB-скриптов.

## 4. Первичный анализ без запуска бинаря

### 4.1. Что выяснить первым

До исполнения нужны ответы на следующие вопросы: это действительно ELF; какая архитектура и разрядность; статическая или динамическая линковка; какие сегменты загружаются; есть ли символы; какой интерпретатор указан; какие свойства защиты заявлены.

В собственном лабораторном проекте:

```bash
sha256sum build/frame_demo
file build/frame_demo
readelf -hW build/frame_demo
readelf -lW build/frame_demo
readelf -SW build/frame_demo
readelf -dW build/frame_demo
readelf -nW build/frame_demo
readelf -Ws build/frame_demo
readelf -rW build/frame_demo
objdump -d -M intel build/frame_demo
```

Назначение флагов и различие ELF-заголовков см. в [документации GNU readelf][readelf]. Для неизвестных файлов эти инструменты тоже запускай в изолированной среде: отсутствие исполнения **целевого** кода не устраняет риски ошибок самих парсеров.

### 4.2. Не включай `ldd` в безусловный recon

Для недоверенного executable `ldd` не является гарантированно пассивной операцией. Его документация прямо предупреждает о возможном исполнении кода. Первичный список зависимостей получай из `DT_NEEDED`, например через `readelf -dW`; учитывай, что это не полный транзитивный граф фактически загруженных библиотек. [Источник: ldd(1)][ldd].

Не путай обычное чтение метаданных `ELF(...)` с любым доступом к свойствам pwntools. В библиотеке есть операции получения карт памяти и библиотек, которые могут исполнять модифицированную копию ELF. Для строгого статического этапа достаточно `readelf`; методы `.libs`, `.maps`, `.libc` не следует считать автоматически безопасными для неизвестного файла. [Источник: ELF API][pwntools-elf].

### 4.3. Автоматизировать сбор, а не выводы

```bash
python3 tools/collect.py build/frame_demo build/report-02
```

Скрипт из приложения фиксирует хеш, архитектуру среды, версии и вывод `readelf`. Он не запускает целевой бинарь, не использует `ldd`, не обращается в сеть и не строит payload. У запускаемых инструментов ограничены время и размер отчёта.

В `manifest.json` проверь:

```text
executed_target: false
unchanged_during_collection: true
commands[*].status: ok
```

`missing`, `failed`, `timeout` и `log_at_limit: true` требуют внимания. Скрипт может оставить частичный отчёт; наличие каталога ещё не означает завершённого анализа.

### 4.4. Не делай поспешных выводов по строкам и именам

Символ `win` может отсутствовать, быть недостижимым или иметь совсем другой контракт. Строка с названием библиотеки не доказывает, что загружен именно этот файл. Отсутствие `.symtab` не означает отсутствия всех динамических символов.

Правильный следующий шаг выбирают по вопросу: **«Что я пока не знаю и какое наблюдение это различит?»**, а не по популярности техники.

## 5. ELF, отображения памяти и загрузчик

### 5.1. Sections и segments — разные представления

**Sections** удобны для компилятора, линкера и анализа: `.text`, `.rodata`, `.data`, `.bss`, таблицы символов и отладочные данные.

**Segments** описывают загрузку и другие runtime-свойства: `PT_LOAD`, `PT_INTERP`, `PT_DYNAMIC`, `PT_GNU_STACK`, `PT_GNU_RELRO`. Во время изучения прав памяти начинай с program headers и карты процесса, а не только с названия секции. [GNU readelf][readelf]; [System V gABI, Program Loading][gabi-elf].

| Область | Обычно содержит | Важная оговорка |
|---|---|---|
| `.text` | Машинный код | Имя секции само не доказывает права отображения |
| `.rodata` | Константные данные | Компоновка зависит от toolchain |
| `.data` | Инициализированные изменяемые данные | Не то же самое, что heap |
| `.bss` | Нулеинициализированные данные | Может занимать память без эквивалентного объёма байтов в файле |
| Stack | Кадры вызовов и временные значения | Не все локальные переменные обязаны находиться здесь |
| Heap и отдельные `mmap` | Динамические выделения | Все malloc-объекты не обязаны лежать в одном непрерывном участке |

### 5.2. Адрес в файле, ELF-адрес и runtime-адрес

Не называй всё это словом «offset» без уточнения.

**File offset** — позиция байта в файле. **ELF virtual address** — адрес в модели загрузки ELF. **Runtime address** — адрес в конкретном процессе после загрузки.

Для участка, представленного байтами соответствующего `PT_LOAD`, преобразование имеет вид:

```text
ELF virtual address = p_vaddr + (file_offset - p_offset)
runtime address     = load_bias + ELF virtual address
```

Формула применяется только внутри подходящего сегмента и его файловой части. Нулевая часть `p_memsz > p_filesz` не имеет аналогичного диапазона содержимого файла. Не подставляй произвольный адрес из стека или другого модуля. Это арифметика загрузки, не доказательство происхождения наблюдаемого указателя. [System V gABI][gabi-elf].

### 5.3. PLT, GOT и relocations

GOT хранит значения, используемые для адресации и динамического связывания; PLT — один из механизмов перехода к внешним функциям. Конкретные обращения могут отличаться из-за оптимизаций, вида relocation и флагов компилятора.

Для собственной программы:

```bash
readelf -rW build/abi_debug
readelf -dW build/abi_debug
objdump -d -M intel build/abi_debug
```

Найди импорт вывода и сопоставь relocation с вызовом в дизассемблере. Не требуй, чтобы каждый ELF имел одинаковый `.plt` или чтобы каждый внешний вызов обязательно проходил через привычный PLT-stub. Смысл немедленного и отложенного связывания описан в [ld.so(8)][loader].

### 5.4. Карта процесса важнее догадки по адресу

В GDB у остановленной собственной программы:

```gdb
info proc mappings
```

На Linux карту процесса предоставляет `/proc/<pid>/maps`: диапазоны, права, смещения и связанный файл, если он есть. Адрес, который «похож на libc», ещё не идентифицирован. Сопоставь его с реальным отображением и точной сборкой. [proc_pid_maps(5)][maps].

## 6. Защиты: что они означают на самом деле

Защиты уменьшают определённые возможности или обнаруживают определённые нарушения. Это не универсальная шкала сложности.

| Механизм | Что проверять | Что нельзя из этого заключать |
|---|---|---|
| Stack protector | Есть ли instrumentation в интересующей функции | «Canary found» не означает защиту каждого объекта и пути |
| PIE | Тип и свойства executable, фактическую загрузку | PIE не равно включённому ASLR |
| ASLR | Политику среды и адреса разных запусков | Одна неизменившаяся карта не характеризует всю систему |
| NX / права страниц | `GNU_STACK`, `PT_LOAD` и runtime mappings | NX не запрещает исполнение уже существующего кода |
| RELRO | `GNU_RELRO`, режим relocation, runtime-права | RELRO не делает всю память процесса read-only |
| FORTIFY | Параметры сборки и доступные проверки libc | Он не заменяет корректную проверку размеров |
| seccomp | Момент установки, правила и действие отказа | Список разрешённых syscall не является полной песочницей |
| CET / CFI | Поддержку, метаданные и фактическое включение | ELF note или инструкция сами по себе не доказывают enforcement |

Источники: [GCC instrumentation][gcc-instrumentation], [GNU ld][ld-options], [Linux seccomp][seccomp-man], [Linux shadow stack][shstk].

### 6.1. Canary

Stack protector добавляет контрольное значение и проверку в выбранные функции. Наличие импорта `__stack_chk_fail` полезно как признак, но интересующий пролог и эпилог нужно смотреть отдельно. Перезапись локального объекта может нарушить данные, не затронув проверяемое значение. [GCC][gcc-instrumentation].

Размер, размещение и устройство guard зависят от платформы и runtime. В типичной glibc x86-64 нулевой младший байт соответствует первому байту в little-endian памяти; это не универсальная спецификация всех ОС и архитектур. Для анализа конкретной версии ориентируйся на её исходники и дизассемблер, а не на комментарий «последний байт всегда ноль». [Исходник glibc][glibc-guard].

### 6.2. PIE и ASLR

PIE — свойство сборки executable. ASLR — поведение среды при размещении объектов. Даже у non-PIE процесса стек и библиотеки могут размещаться по-разному. В GDB отдельно проверяй:

```gdb
show disable-randomization
```

Чтобы отладчик не просил ОС отключать ASLR для запускаемой программы:

```gdb
set disable-randomization off
```

Обрати внимание на двойное отрицание: `off` здесь означает «не отключать рандомизацию». Это настройка данной сессии GDB, не глобальное изменение ядра. [GDB: Starting][gdb-start].

### 6.3. NX

Право на исполнение — свойство отображения страницы. `GNU_STACK` без `E` показывает запрос на неисполняемый стек; это не доказательство отсутствия любых writable+executable отображений в программе на всём протяжении работы. Для runtime-проверки смотри карту процесса. [GNU ld][ld-options]; [proc_pid_maps(5)][maps].

### 6.4. RELRO

В обычном GNU ELF toolchain **Partial RELRO** защищает часть relocation-related данных, оставляя возможность отложенного связывания. **Full RELRO** обычно соответствует RELRO вместе с немедленным связыванием (`-z relro -z now`). Проверяй и заголовки, и динамические флаги: названия уровней — сокращение, а не точная карта всех страниц. [GNU ld][ld-options].

<a id="abi"></a>
## 7. Лаборатория A: ABI, регистры и стек

**Цель:** увидеть обычный вызов функции, аргументы и различия сборок.  
**Файлы:** `src/abi.c`, `build/abi_debug`, `build/abi_opt`.  
**Ожидаемый результат обеих программ:** `sum=28`.

### 7.1. Базовая модель System V AMD64

Для рассматриваемой функции с семью аргументами типа `long`:

| Значение | Место при входе в функцию |
|---|---|
| Аргументы 1–6 | `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9` |
| Аргумент 7 | В памяти стека |
| Возвращаемый `long` | `RAX` |
| Адрес возврата после обычного `call` | На вершине обычного стека при входе |

Это не полное правило для любых типов: float/vector, aggregate, variadic и возвращаемые структуры требуют дополнительных правил ABI. [System V AMD64 ABI, §3.2][abi-spec].

Системный вызов Linux x86-64 использует другое соглашение для четвёртого аргумента: `R10`, а не `RCX`; номер вызова передаётся в `RAX`. Не смешивай вызов C-функции `read()` и переход к ядру. [syscall(2)][syscall].

### 7.2. Собрать и посмотреть машинный код

```bash
make all
./build/abi_debug
./build/abi_opt
objdump -d -M intel --disassemble=sum7 build/abi_debug
objdump -d -M intel --disassemble=sum7 build/abi_opt
```

В исходнике `noinline` оставляет функцию отдельной, а `volatile`-массив делает обращения к нему наблюдаемыми для компилятора. Это искусственно выбранные свойства учебного примера, не типичная гарантия для произвольного оптимизированного кода.

### 7.3. Остановиться именно на входе

```bash
gdb -q -nx -iex 'set auto-load off' --args ./build/abi_debug
```

В GDB:

```gdb
set pagination off
set disassembly-flavor intel
set disable-randomization off
break *sum7
run
info registers rdi rsi rdx rcx r8 r9 rsp rbp
x/2gx $rsp
p/x ((unsigned long)$rsp & 0xf)
disassemble /r sum7
```

На первом машинном адресе `sum7`, до изменения стека её прологом, ожидаются аргументы `1, 2, 3, 4, 5, 6` в указанных регистрах. Вторая восьмибайтовая ячейка от текущего `RSP` содержит `7`.

Для этого обычного вызова на входе ожидается `RSP mod 16 = 8`: сам `call` помещает восьмибайтовый адрес возврата. Более сильные требования выравнивания для отдельных vector-аргументов относятся к другим случаям. Не проверяй это равенство в произвольной точке тела функции. [System V ABI, §3.2.2][abi-spec].

### 7.4. Почему картинка стека — только модель

При использовании frame pointer картина около `RBP` часто выглядит так:

```text
Более высокие адреса
    стековые аргументы
    адрес возврата
    сохранённое значение RBP   ← RBP после пролога
    локальные данные / padding / служебные значения
Более низкие адреса
```

Но компилятор может не использовать `RBP` как frame pointer, хранить значения в регистрах, переупорядочивать размещение объектов или выполнять tail call. Эпилог не обязан быть именно `leave; ret`. [GDB: Optimized Code][gdb-optimized].

### 7.5. Проверка понимания

Сравни `abi_debug` и `abi_opt` и запиши: где находятся аргументы в момент входа, как изменяется `RSP`, используется ли `RBP` как база кадра, каким путём получается итоговое значение.

**Критерий готовности:** ты можешь объяснить конкретные инструкции своего файла, не ссылаясь на «всегда одинаковый стек».

<a id="protocol"></a>
## 8. Лаборатория B: байты, протокол и границы

**Цель:** перестать путать сообщения, строки и отдельные операции чтения.  
**Файлы:** `src/frame.*`, `src/frame_main.c`, тесты протокола.  
**Контракт:** один запрос на процесс; вход завершается EOF.

### 8.1. Формат нашего сообщения

```text
[4 байта длины, unsigned little-endian][ровно N байтов данных][EOF]
0 ≤ N ≤ 64
```

Содержимое — произвольные байты, включая `00`, `ff` и `0a`. Программа не интерпретирует его как C-строку. Дополнительные байты после объявленного содержимого недопустимы. EOF здесь намеренно является частью учебного протокола, а не общим правилом для всех сервисов.

Успех:

```text
stdout: OK <длина> <hex>
stderr: пусто
exit code: 0
```

Ошибка формата: код 2 и диагностика в stderr. Ошибка ввода-вывода: код 1.

### 8.2. Передать штатный запрос

```bash
python3 - <<'PY' | ./build/frame_demo
import struct
import sys
payload = b"A\x00\xff\n"
sys.stdout.buffer.write(struct.pack("<I", len(payload)) + payload)
PY
```

Ожидается:

```text
OK 4 4100ff0a
```

Здесь `payload` означает содержимое **обычного сообщения**, не exploit.

### 8.3. Почему `read()` не означает «получить всё»

`read(fd, buf, count)` может вернуть меньше запрошенного количества, ноль при EOF либо ошибку. Значение типа `ssize_t` нужно проверить до преобразования к `size_t`; иначе отрицательная ошибка может превратиться в большое положительное число. Прочитанные байты не получают автоматический завершающий `\0`. [read(2)][read].

Наш `frame_main.c` накапливает ввод с проверкой `EINTR`, никогда не пишет за границу массива и ограничивает объём входа. Парсер работает с уже имеющимся диапазоном байтов и отдельно проверяет длину.

### 8.4. Чем опасны удобные строковые операции

`strip()` удаляет определённые байты с обоих концов. Это подходит не каждому бинарному протоколу. `sendline()` добавляет перевод строки. `recvline()` предполагает разделитель, который тоже должен быть частью контракта. Для бинарного формата выбирай операцию по формату, а не по привычке. [pwntools tubes][pwntools-tubes].

На собственном примере можно проверить разницу: дополнительный перевод строки после сообщения делает вход невалидным. Не «исправляй» это изменением объявленной длины, пока не решил, что именно относится к данным.

### 8.5. Что проверяют 73 теста

Тесты включают все допустимые длины от 0 до 64, невалидные заголовки, превышение лимита, несовпадение длины, лишний байт и отправку сообщения побайтными записями. Последняя проверка не обещает, что ядро отдаст по одному байту за каждый `read`: границы операций записи не являются гарантированными границами чтений.

```bash
python3 tests/test_protocol.py ./build/frame_demo
```

**Критерий готовности:** ты можешь назвать разделитель, ограничения, правила EOF и ожидаемые коды завершения, не открывая реализацию.

<a id="bugs"></a>
## 9. Классы ошибок памяти и чисел

В PWN важно сначала понять нарушенный инвариант. Один и тот же crash может быть следствием разных причин.

| Класс | Что нарушено | Что фиксировать при анализе |
|---|---|---|
| Out-of-bounds read | Чтение вышло за разрешённый диапазон объекта | Базу, размер объекта, индекс и ширину операции |
| Out-of-bounds write | Запись вышла за разрешённый диапазон | Место записи и объект назначения |
| Use-after-free | Обращение после окончания времени жизни | Где объект создан, освобождён и затем используется |
| Double free | Повторное освобождение одного владения | Пути очистки и aliases |
| Integer overflow / truncation | Числовая модель перестала соответствовать размеру | Типы до и после операции, знаковость, порядок проверок |
| Format string | Данные интерпретируются как управляющая строка формата | Происхождение формата и соответствие аргументов |
| Uninitialized read | Значение используется до определённой инициализации | Все входящие ветви и частичные записи |
| Race / lifetime race | Неправильная координация доступа или освобождения | Потоки, владение, happens-before |

Это описания классов, не доказательство эксплуатируемости. Терминология: [CWE-787][cwe-oob], [CWE-416][cwe-uaf], [CWE-134][cwe-format].

### 9.1. Stack buffer overflow

Стековый массив имеет границы на уровне C-объекта. Физическое соседство с другими объектами не даёт права писать дальше. Падение может произойти в момент доступа, на проверке stack protector или значительно позже.

Не используй правило «размер буфера плюс восемь» как описание любого stack frame. Padding, выравнивание, наличие служебных значений и оптимизации меняют размещение. А отсутствие canary не доказывает существования записи до адреса возврата.

### 9.2. Integer errors

Размер проверяют **до** потенциально переполняющей операции. Для умножения размеров при `item_size != 0`:

```text
count ≤ SIZE_MAX / item_size
```

После проверки произведение помещается в `size_t`. В приложении это реализует `checked_product()`, включая нулевой размер и некорректный указатель результата.

Signed overflow в C не следует считать гарантированным циклическим переходом. Для unsigned действуют правила модульной арифметики, но логика выделения памяти всё равно может стать неверной. Для реального кода доступны также checked builtins GCC; выбор зависит от требований к переносимости. [GCC overflow builtins][gcc-overflow]; [UBSan][ubsan].

Отдельно проверь сложение служебного заголовка, сужение типа, преобразование отрицательной длины и единицы измерения: число элементов не равно числу байтов.

### 9.3. Format string

Формат — это отдельный управляющий язык. При обычном выводе пользовательского текста его не следует использовать как саму строку формата. Для текста с гарантированным нулевым завершением подходит постоянный формат; для байтов с известной длиной — длино-ориентированный вывод. Подробности типов и преобразований см. в [printf(3)][printf].

В нашей программе формат каждого `printf` постоянный. Отдельный аргумент содержит число либо байт. Это позволяет проверить интерфейс без лабораторной уязвимости.

### 9.4. Нарушение данных не равно перехвату управления

Баг может менять логическое состояние программы, не касаясь return address: длину, индекс, флаг состояния, счётчик ссылок. И наоборот, завершение на `ret` не доказывает полноценного управляемого выполнения. В отчёте различай root cause, наблюдаемое последствие и недоказанное расширение последствий.

<a id="debugging"></a>
## 10. Лаборатория C: отладка и проверка гипотез

**Цель:** связать вход, проверку в коде и результат процесса, не подменяя наблюдения догадками.

### 10.1. Подготовить известный вход

```bash
mkdir -p evidence
python3 - <<'PY'
from pathlib import Path
import struct
Path("evidence/valid.bin").write_bytes(struct.pack("<I", 3) + b"abc")
Path("evidence/rejected.bin").write_bytes(struct.pack("<I", 65))
PY
```

Это два теста собственного парсера: штатное сообщение и отказ при превышении установленного лимита.

### 10.2. Следить за проверкой

```bash
gdb -q -nx -iex 'set auto-load off' --args ./build/frame_demo
```

```gdb
set pagination off
set disassembly-flavor intel
set disable-randomization off
break frame_parse
run < evidence/valid.bin
info args
list
next
info locals
```

Повтори с `evidence/rejected.bin`. Используй `next`, чтобы увидеть ветвление и значение статуса. Не привязывай текст гайда к фиксированному номеру строки: он меняется при редактировании кода.

`-nx` отключает init-файлы GDB; `-iex 'set auto-load off'` выполняется до загрузки executable и отключает дополнительные автозагрузки. Это не превращает запуск неизвестной программы в безопасную операцию — он всё ещё требует изоляции. [GDB auto-loading][gdb-autoload].

### 10.3. Минимальный набор команд

| Задача | Команда |
|---|---|
| Где остановились | `x/i $pc`, `bt` |
| Какие значения видит исходный уровень | `info args`, `info locals` |
| Какие регистры изменились | `info registers` |
| Посмотреть инструкции | `disassemble /r frame_parse` |
| Шагнуть по исходному коду | `next`, `step` |
| Шагнуть по инструкции | `nexti`, `stepi` |
| Узнать карту памяти | `info proc mappings` |
| Посмотреть байты известного объекта | `x/16bx buf` при допустимом диапазоне |
| Найти следующую запись в переменную | `watch variable` при доступном символе |

Перед разыменованием адреса убедись, что он относится к ожидаемому объекту. В optimized build переменная может быть `optimized out`; это свойство доступной отладочной информации, не автоматическое доказательство повреждения памяти. [GDB: Optimized Code][gdb-optimized].

### 10.4. Если исследуемая программа уже упала

Сохрани точный вход и команду запуска. Зафиксируй сигнал, текущую инструкцию, относящиеся к ней регистры, backtrace и карту памяти. Сначала определи тип операции — чтение, запись, переход, явный abort — и лишь затем объясняй причину.

**Адрес инструкции и адрес ошибочного доступа — разные величины.** При сбое косвенного перехода или `ret` текущий `RIP` не обязан содержать значение, которое пытались использовать как новый адрес. Нельзя считать один регистр универсальным источником сведений о crash. Конкретную семантику сверяй с машинной инструкцией и сигналом; архитектурные детали описаны в [Intel SDM][intel-sdm].

### 10.5. Core dump: почему нет `./core`

Расположение, имя и сам факт создания дампа зависят от лимитов, `core_pattern`, прав и обработчика системы. Прочитать настройки можно без изменения системы:

```bash
ulimit -c
cat /proc/sys/kernel/core_pattern
```

Не переписывай глобальный `core_pattern` ради одной задачи. Если дамп сохраняет системная служба, используй её штатные средства и ограничь доступ к полученному файлу. [core(5)][core].

**Критерий готовности:** для каждого теста указаны проверяемая гипотеза, остановка, наблюдение и ожидаемый исход.

## 11. Лаборатория D: проверяем свойства сборки

**Цель:** сопоставить compiler/linker flags, ELF-метаданные и исполнение.

### 11.1. Параметры нашего Makefile

```text
-fstack-protector-strong
-fPIE / -pie
-Wl,-z,relro,-z,now,-z,noexecstack
-Wformat=2 -Wformat-security
```

Это явно выбранные настройки, а не предположение о дефолтах конкретного дистрибутива. Для debug-сборки дополнительно используются `-O0 -g3 -fno-omit-frame-pointer`. Значение отдельных флагов: [GCC][gcc-instrumentation], [GNU ld][ld-options].

### 11.2. Проверить ELF

```bash
readelf -hW build/abi_debug
readelf -lW build/abi_debug
readelf -dW build/abi_debug
readelf -Ws build/abi_debug
objdump -d -M intel --disassemble=sum7 build/abi_debug
```

Ожидаемые признаки нашей сборки: `DYN` как ELF-тип PIE executable, `GNU_STACK` без execute-флага, сегмент `GNU_RELRO`, признак немедленного связывания в динамических флагах, проверка stack protector в подходящей функции.

Точное оформление вывода и названия dynamic flags могут отличаться. `DYN` без дополнительного контекста не различает PIE executable и shared object.

### 11.3. Сопоставить с двумя запусками

В GDB:

```gdb
set disable-randomization off
break main
run
info proc mappings
run
info proc mappings
```

Сравни отображение executable и библиотек. При активном ASLR обычно отличаются базовые адреса. Совпадение отдельного диапазона не опровергает наличие рандомизации; проверь политику и несколько объектов. [GDB][gdb-start].

Не нужно отключать защиты, чтобы понять их устройство. Если тест не совпал с ожидаемым, сначала проверь команду линковки, тип файла, настройки GDB и фактический runtime.

**Критерий готовности:** для каждого свойства есть конкретный источник сведений и оговорка, что именно он не доказывает.

<a id="heap"></a>
## 12. Heap: allocator, владение и время жизни

### 12.1. Две модели, которые нельзя смешивать

С точки зрения программы `malloc` возвращает память под объект заданного размера. С точки зрения allocator запрос обслуживается из внутренних структур, которые могут учитывать классы размеров, арены, кэши потоков и отдельные отображения.

Знание внутреннего размера allocation не расширяет допустимые границы C-объекта. И успешный `free` не гарантирует немедленного удаления страницы из адресного пространства. Контракт malloc/free описан в [malloc(3)][malloc].

### 12.2. Термины glibc allocator

| Термин | Смысл для чтения исходников |
|---|---|
| Chunk | Внутренняя единица учёта allocation |
| Arena | Структуры allocator, связанные с обслуживанием выделений |
| Bin | Категория/структура хранения свободных блоков |
| Tcache | Кэш определённых свободных allocation, связанный с потоком |
| Consolidation | Объединение совместимых свободных областей |
| Top chunk | Особая свободная область в модели allocator |

Это не стабильный внешний ABI. Размеры, условия переходов и проверки нужно читать для выбранной сборки. Для настройки malloc см. [glibc tunables][malloc-tunables]; для конкретной реализации — [malloc.c выбранной версии][glibc-malloc].

### 12.3. Что действительно нужно понять до продвинутых техник

Начни с последовательности **создание → передача владения → использование → освобождение**. Для каждого указателя выясни, кто его освобождает, какие aliases остаются, может ли объект быть перемещён, кто синхронизирует доступ.

Присвоение `owner = NULL` полезно для этой переменной, но не изменяет другие копии указателя. `realloc` может переместить allocation; старые ссылки на внутренние данные нельзя автоматически считать действительными. [malloc(3)][malloc].

### 12.4. Почему allocator-инструкции привязаны к версии

Safe-Linking и проверки целостности структур — механизмы конкретных реализаций, а не «шифрование всей кучи». Изменение allocator может сделать старое описание неприменимым даже при похожем выводе программы. Наличие привычного имени внутреннего символа тоже не доказывает его прежней роли. [Исходник glibc malloc][glibc-malloc].

Для анализа фиксируй точный файл libc и его хеш, build ID, архитектуру, threading, настройки allocator и наличие sanitizer. Не переноси смещения и переходы состояний из чужого write-up без проверки совпадения среды.

### 12.5. Что sanitizer меняет в наблюдении

ASan добавляет свою модель отслеживания памяти и может менять allocator-поведение и layout. Он удобен для обнаружения неверного доступа, но трасса ASan-сборки не является точной моделью размещения объектов обычной production-сборки. [AddressSanitizer][asan].

<a id="ownership-lab"></a>
## 13. Лаборатория E: наблюдаем владение памятью

**Цель:** проследить нормальный lifetime, не читая освобождённую память.  
**Файл:** `src/ownership.c`.

```bash
./build/ownership
```

Ожидается:

```text
live object: example
ownership released
```

В программе один владелец `owner` и временная заимствованная ссылка `borrowed`. Использование завершается до освобождения. Не печатай содержимое объекта после `free` ради проверки «остались ли байты»: это уже неверный доступ, даже если адрес всё ещё отображён.

В GDB поставь остановку на `main`, пройди выделение, копирование и завершение заимствования. Сопоставь исходник с машинным кодом, но не делай предположения о том, какой внутренний bin должен использовать allocator: цель этой лаборатории — контракт владения.

**Критерий готовности:** ты можешь объяснить, почему обнуление только одной переменной не исправляет существующий dangling alias, и где должен завершаться lifetime каждого заимствования.

<a id="seccomp"></a>
## 14. Лаборатория F: seccomp и системные вызовы

### 14.1. Что фильтруется

Seccomp-BPF принимает решение по данным системного вызова, включая архитектуру, номер и значения аргументов. Фильтр не является произвольным C-кодом, читающим содержимое указателя на строку. Он также не заменяет правила доступа к файлам, пространства имён или разделение привилегий. [Linux seccomp filter][seccomp-kernel].

Результат отказа зависит от policy: возможны завершение процесса, сигнал, возврат заданной ошибки и другие действия. Поэтому `SIGSYS` и `EPERM` не взаимозаменяемы, а отсутствие crash ещё не означает, что syscall разрешён. [seccomp(2)][seccomp-man].

### 14.2. Собственный минимальный фильтр

`src/seccomp_demo.c` сначала устанавливает `no_new_privs`, затем фильтр для native x86-64. В этой учебной программе разрешены только `write`, `exit`, `exit_group`; остальные вызовы получают `EPERM`. Для неподходящей архитектуры предусмотрено прекращение процесса.

После установки фильтра программа проверяет **собственный** `getpid` и печатает результат. Вывод выполняется через разрешённый syscall, без последующего использования malloc или обычного `exit()`.

```bash
make sandbox-test
```

Ожидается:

```text
PASS: getpid blocked with EPERM
```

Проверка трассой собственной программы:

```bash
mkdir -p evidence
strace -o evidence/seccomp.txt \
  -e trace=prctl,getpid,write,exit,exit_group \
  ./build/seccomp_demo
```

В успешном случае после установки фильтра `getpid` завершается с `EPERM`, а `write` работает. Эта последовательность наблюдалась только на выполненном пути; одна трасса не заменяет чтение всей policy. [strace manual][strace]; [seccomp(2)][seccomp-man].

### 14.3. Почему это не готовая production-policy

Фильтр демонстрационный: он не ограничивает аргументы `write`, не описывает полный жизненный цикл сложного приложения, не решает вопросы запуска потоков и не управляет уже открытыми дескрипторами. После установки программа специально завершает работу простым путём.

При проектировании sandbox нужно отдельно анализировать доступные файлы и дескрипторы, права, сеть, namespace, момент установки и наследование ограничений. Способность выполнять только `read` и `write` сама по себе ничего не говорит о ценности доступных данных. [Linux seccomp][seccomp-kernel].

### 14.4. Откат

Ограничения устанавливаются только для процесса демонстрации, не для твоего shell. Завершение этого процесса завершает эксперимент. Не требуется менять sysctl или настройки безопасности всей машины.

**Критерий готовности:** ты различаешь filter action, ошибку самого syscall и ограничение внешней среды.

<a id="advanced"></a>
## 15. Продвинутые техники: карта понятий

Этот раздел нужен для чтения исследований и write-up. Название техники описывает идею, но не доказывает её применимости к исследуемой программе.

### 15.1. Повторное использование кода

**ret2win** — учебное название перенаправления выполнения в уже существующую функцию. **ret2libc** — использование уже загруженного библиотечного кода. **ROP** — более общий подход к выполнению последовательностей существующих фрагментов кода; NX сам по себе не запрещает такой класс поведения. Исторический источник ROP: [Shacham, CCS 2007][rop-paper].

Для понимания этих названий полезнее знать контракт функции, ABI и последствия перехода, чем запоминать один набор байтов. В обычном корректном вызове важны не только адрес, но и типы аргументов, состояние памяти, stack alignment и дальнейшее завершение выполнения.

### 15.2. ROP, JOP, COP и stack pivot

| Термин | Концепция | Что изучать для понимания |
|---|---|---|
| ROP | Повторное использование кода с последовательностью возвратов | Семантику инструкций и ограничения return-пути |
| JOP | Повторное использование с косвенными переходами | Indirect branches и ограничения целей |
| COP | Повторное использование через вызовы | Соглашение о вызовах и call/return-модель |
| Stack pivot | Изменение области, используемой как рабочий стек | Смысл `RSP`, допустимые отображения и unwind |

Нельзя считать, что наличие инструкции `ret` или косвенного перехода в файле само доказывает достижимость произвольного поведения. Shadow stack и CFI проверяют разные аспекты потока управления. [Linux CET][shstk]; [Clang CFI][cfi].

**Безопасное упражнение:** сравни обычные `call` и `ret` в `abi_debug`, проверь передачу аргументов и восстановление состояния после вызова. Это создаёт модель корректного поведения, относительно которой можно понимать нарушение.

### 15.3. SROP и восстановление контекста

При обработке сигнала ОС и runtime организуют сохранение и последующее восстановление состояния выполнения. Название SROP относится к злоупотреблению этим механизмом. Для понимания требуется изучить signal frame, ABI восстановления и конкретные ограничения платформы; одного слова `sigreturn` в allowlist недостаточно для вывода о последствиях. Обычная семантика описана в [sigreturn(2)][sigreturn].

В этом руководстве не создаются искусственные signal frames. Практическая подготовка — понимать, чем обработчик сигнала отличается от обычного вызова и почему восстановление регистров является отдельной границей доверия.

### 15.4. Динамический загрузчик и ret2dlresolve

Динамическое связывание использует ELF-метаданные, символы и relocation. Термин ret2dlresolve относится к злоупотреблению этим механизмом. Полезные основы для чтения подобных материалов: кто выполняет разрешение символа, когда оно происходит, к какому модулю относится запись и какие данные после связывания становятся read-only. [ld.so(8)][loader].

Не требуется собирать поддельные структуры, чтобы увидеть штатное связывание. На собственной программе можно получить диагностику загрузчика:

```bash
mkdir -p evidence
LD_DEBUG=libs,bindings ./build/abi_debug 2> evidence/loader.txt
```

Это **запуск** доверенной лабораторной программы, не статическая проверка неизвестного executable. Значение `LD_DEBUG` действует только на эту команду. [ld.so(8)][loader].

### 15.5. Heap exploitation и FSOP

Эти названия обозначают разные способы злоупотребления ошибками lifetime, внутренним состоянием allocator либо инфраструктурой потокового ввода-вывода. Здесь особенно опасно переносить структуры и предположения между версиями libc.

Для чтения таких материалов сначала установи, какая структура принадлежит приложению, какая — runtime, кто вправе её менять и какие проверки выполняются на пути её использования. Наличие UAF не означает, что достижимо любое произвольное изменение состояния. Контракт объектов и внутреннюю реализацию рассматривай отдельно. [glibc malloc][glibc-malloc]; [stdio(3)][glibc-streams].

### 15.6. Data-only нарушения

Не каждое последствие ошибки связано с выполнением нового или повторно используемого кода. Повреждение длины, статуса объекта или другого значимого поля может менять поведение в рамках обычного control flow. Поэтому модель безопасности должна включать целостность данных и корректность переходов состояния, а не только return address. Это аналитический вывод из разделения контроля потока и данных; он не определяет автоматически последствия конкретного бага.

<a id="modern"></a>
## 16. CET, CFI и другие современные защиты

### 16.1. Проверяй четыре слоя

```text
Поддержка процессором
        ↓
Поддержка ОС и runtime
        ↓
Сборка с нужными свойствами
        ↓
Фактическое включение для процесса
```

Пропуск любого слоя делает заключение «защита активна» недостаточно обоснованным. [Linux shadow stack][shstk].

### 16.2. Shadow stack и indirect branch tracking

Shadow stack предназначен для контроля возвратов с использованием дополнительного состояния. IBT относится к косвенным переходам. Это разные компоненты; нельзя считать их одним флагом «CET». Конкретная доступность в user space зависит от ОС, загрузчика и сборки. Для своего ядра используй соответствующую версию документации. [Linux CET documentation][shstk].

`readelf -nW` показывает GNU properties файла. Это один источник сведений, но не полный runtime-вердикт. Аналогично, `endbr64` в дизассемблере сам по себе не доказывает, что аппаратная проверка используется данным процессом.

### 16.3. CFI

Control-Flow Integrity ограничивает допустимые цели определённых переходов в соответствии с выбранной моделью. Разные режимы CFI проверяют разные конструкции: например, косвенные вызовы или виртуальную диспетчеризацию C++. Требования к LTO, visibility и межмодульному взаимодействию зависят от режима. Не своди CFI к универсальному запрету всех изменений управления. [Clang CFI][cfi].

### 16.4. За пределами x86-64

На AArch64 дополнительно встретятся pointer authentication, branch target identification и memory tagging. Это разные механизмы с разными предпосылками. Нельзя переводить наличие одного из них в утверждение о полной защите памяти. Для обзорного знакомства с tagging см. [Linux MTE][mte]; для конкретного ABI — [Arm ABI specifications][arm-abi].

<a id="optimized"></a>
## 17. Оптимизации, stripped ELF и C++

### 17.1. Дизассемблер показывает результат компиляции

Компилятор может встроить функцию, убрать значение, объединить ветви, переиспользовать регистр или заменить вызов хвостовым переходом. Отладочная информация описывает связь с исходником настолько, насколько её удалось сохранить.

Поэтому две сборки из одного исходника могут иметь разные кадры, адреса и места остановок. Debug-сборка удобна для понимания, но её размещение объектов нельзя считать доказательством размещения в release. [GDB optimized code][gdb-optimized].

### 17.2. Stripped не значит «анализ невозможен»

При отсутствии обычных символов остаются другие источники: entry point, program headers, динамические импорты, relocation, константы и машинные инструкции. Разделяй метаданные, которые действительно есть в файле, и имена, которые инструмент назначил эвристически. [GNU readelf][readelf].

Сохраняй найденные функции под содержательными рабочими именами, но отмечай их как свои обозначения. Псевдокод декомпилятора — гипотеза о высокоуровневой структуре, не исходный текст программы.

### 17.3. C++ добавляет lifetime и object model

Кроме обычных указателей возникают виртуальная диспетчеризация, destructors, исключения и сложные связи владения. Ошибка может проявляться при очистке или выходе по исключению, а не на основном пути. Поддержка отдельных C++-проверок в sanitizer и CFI не означает проверки всех правил языка. [Clang CFI][cfi]; [UBSan][ubsan].

Практический вопрос ревью: кто владеет объектом на каждом пути, какие ссылки могут пережить его уничтожение и отличается ли cleanup при ошибке.

### 17.4. Fork, exec и потоки

`fork()` и `execve()` — разные события. Первое создаёт дочерний процесс с наследуемым состоянием, второе заменяет образ процесса. Потоки делят адресное пространство, но имеют собственные стеки и thread-local state. Это существенно для интерпретации повторных запусков и lifetime. [fork(2)][fork]; [execve(2)][execve].

Не считай каждое новое соединение новым независимым состоянием программы, а каждый новый PID — гарантированно новой загрузкой того же типа. Сначала исследуй модель запуска.

<a id="testing"></a>
## 18. Sanitizers, граничные тесты и fuzzing

### 18.1. Что проверяется в лабораториях

```bash
make sanitize
```

Профиль использует `-fsanitize=address,undefined`, отладочные данные и остановку при найденной sanitizer-ошибке. Невалидный вход парсера должен отклоняться штатно: кодом 2, а не crash или sanitizer-report.

ASan обнаруживает определённые ошибки адресации и lifetime. UBSan проверяет выбранные нарушения правил выполнения C/C++. Это динамические инструменты: они наблюдают только исполненные участки. [ASan][asan]; [UBSan][ubsan].

### 18.2. Три различных результата

| Результат | Что он означает |
|---|---|
| Parser отказал согласно контракту | Нормальная обработка невалидного запроса |
| Sanitizer сообщил об ошибке | Наблюдаемое нарушение требует расследования |
| Процесс убит или истёк timeout | Причина пока не определена: среда, ресурсы, баг, протокол |

Не называй все три результата «падением» и не теряй stderr. Не добавляй автоматические повторы, которые скрывают нестабильность.

### 18.3. Как выбирать граничные тесты

Для каждого размера рассмотри ноль, минимальное допустимое значение, максимум и превышение максимума. Для каждого формата — неполный заголовок, неполное тело, лишние байты и допустимые необычные значения внутри тела.

У нашего парсера важны отдельные инварианты: успешный результат имеет длину не более 64; возвращённое представление относится к исходному буферу; ошибка сбрасывает выходное представление; недопустимая длина отвергается до использования тела. Эти свойства прямо связаны с исходным кодом и unit-тестами.

### 18.4. Где здесь fuzzing

Coverage-guided fuzzing расширяет набор исследованных входов на основании наблюдаемого покрытия. Но качество результата зависит от harness: детерминированности, сброса состояния, ограничений ресурсов и того, какие ошибки считаются значимыми. [LLVM libFuzzer][libfuzzer].

Для собственного парсера разумная последовательность — сначала unit-тесты контракта, затем граничные случаи, затем ограниченное генеративное тестирование. Найденный проблемный вход после исправления становится regression test. Автоматический поиск входов не доказывает причину ошибки и не определяет её последствия.

### 18.5. Потоки требуют отдельного инструмента

ASan не заменяет детектор data race. ThreadSanitizer предназначен для отдельного класса проблем и имеет свои ограничения. Профили ASan и TSan не следует бездумно объединять; GCC явно ограничивает некоторые сочетания sanitizer. [TSan][tsan]; [GCC instrumentation][gcc-instrumentation].

### 18.6. Отрицательные результаты тоже ограничены

«73 теста прошли» означает именно это. Это не «парсер доказанно безопасен», не полное покрытие всех входов и не сертификат отсутствия UB в любой сборке. При изменении кода тесты и критерии нужно пересматривать.

<a id="reproduction"></a>
## 19. Почему одинаковый код ведёт себя по-разному

### 19.1. Сравни окружение до изменения программы

| Отличие | Что оно может менять |
|---|---|
| Другой compiler/flags | Машинный код и размещение значений |
| Другая libc/loader | Связывание, allocator и runtime-поведение |
| Другой kernel/CPU | Доступность механизмов и системных вызовов |
| ASLR/GDB | Адреса и условия наблюдения |
| PTY вместо pipe | Буферизацию и терминальное поведение |
| Другой cwd/argv | Пути и контракт запуска |
| Sanitizer | Layout, checks и время выполнения |
| Threads/process model | Порядок событий и lifetime |

### 19.2. Сначала идентифицируй файлы

У двух копий сравни SHA-256 и build ID. У динамического executable прочитай интерпретатор из `PT_INTERP` и `DT_NEEDED`. Запись `libc.so.6` — имя зависимости, не уникальная идентичность файла. Детали поиска библиотек и различия `RPATH`/`RUNPATH` описаны в [ld.so(8)][loader].

Не подменяй системную libc рабочей машины ради эксперимента. Изоляция user space или отдельная VM обратимее и не затрагивает другие процессы.

### 19.3. «Файл есть, а запускается как No such file»

Одно из возможных объяснений — отсутствующий ELF-интерпретатор. Это проверяется чтением program headers без запуска файла:

```bash
readelf -lW build/frame_demo
```

Это не единственная возможная причина; сообщение нужно соотнести с фактическим путём запуска и результатами системного вызова. Поведение загрузки и ошибки описаны в [execve(2)][execve].

### 19.4. Протокол важнее транспортной обёртки

Наш `frame_demo` ждёт EOF. Если отправить корректные байты и не завершить вход, он может ждать дальше. Это не ошибка размера, не ASLR и не проблема компилятора — таков контракт.

В `tools/pwn_local.py` явно используется `shutdown("send")`, затем ограниченное ожидание ответа и выхода процесса. Внешней сети и режима подключения к произвольному адресу в этом примере нет.

<a id="other-platforms"></a>
## 20. Другие архитектуры и kernel PWN

### 20.1. Не переносить x86-64 автоматически

В i386 отличаются разрядность и соглашения. В AArch64 другая роль регистров и link register. Endianness нужно читать из формата и ABI, а не выводить из языка исходника. Смешение ISA, ABI и ОС — частая причина неверной интерпретации данных. [syscall(2)][syscall]; [Arm ABI][arm-abi].

Эмуляция помогает запускать другую архитектуру, но не означает, что измерены свойства реального CPU и полноценного целевого ядра. Поэтому результат запуска эмулятора нужно маркировать отдельно.

### 20.2. Kernel — отдельная среда, а не «ещё один ELF»

Для ошибок в ядре отличаются жизненный цикл объектов, синхронизация, привилегии, allocator, диагностика и модель отказа. Crash может затронуть всю гостевую ОС. Начинать следует с собственного тестового ядра в VM и его средств диагностики, не с загрузки чужого модуля на основной хост.

KASAN предназначен для обнаружения определённых ошибок памяти в ядре и имеет несколько режимов с разными требованиями. [Linux KASAN][kasan].

Этот файл не является полным курсом kernel exploitation, Windows PE, browser exploitation или всех ABI. Для них нужна отдельная среда и отдельный набор проверяемых предпосылок.

## 21. Диагностическая таблица

Начинай с самого дешёвого наблюдения, которое различает вероятные причины.

| Симптом | Что проверить первым | Чего не делать автоматически |
|---|---|---|
| ELF не запускается | Архитектуру, interpreter, права, точный путь | Не заменять libc хоста |
| GDB показывает постоянные адреса | `show disable-randomization` | Не менять глобальный ASLR |

| Ответ отличается на один байт | Добавленный `\n`, кодирование, trimming | Не применять `strip()` ко всем ответам |
| Только sanitizer-build ведёт себя иначе | Sanitizer-report, layout и runtime | Не переносить его адреса в обычную сборку |
| `SIGSYS` либо `EPERM` | Policy и syscall на данном пути | Не считать их одним видом отказа |
| Heap выглядит иначе | libc, threading, allocator settings, instrumentation | Не переносить внутренние смещения из другой версии |
| Короткое чтение | Возвращённое `ssize_t`, EOF, `EINTR` | Не считать один `read` полным сообщением |
| Неверная длина после ошибки I/O | Преобразование signed → unsigned | Не использовать результат до проверки |
| Сборщик дал `PARTIAL` | Статус каждой команды и лимит вывода | Не объявлять отчёт полным |
| Seccomp-тест дал 77 | Сообщение `prctl` и возможности среды | Не расширять привилегии всего хоста |
| Путь исследования противоречит наблюдению | Исходную предпосылку | Не добавлять случайные изменения до совпадения |

## 22. Как оформлять выводы и материалы для RAG

### 22.1. Шаблон карточки исследования

```yaml
case_id: local-frame-parser
scope: own-local-lab
architecture: x86_64
os: Linux
binary_sha256: "заполнить по фактическому файлу"
libc_build: "заполнить; unknown, если не установлено"

  input: "evidence/rejected.bin"
  expected: "reject malformed frame"
  actual: "заполнить по запуску"
  exit_code: null
hypothesis: "длина проверяется до использования тела"
evidence:
  - "путь к логу и точное место"
limitations:
  - "проверены только перечисленные входы и сборка"
next_check: "одна проверка, различающая оставшиеся объяснения"
```

Не заполняй неизвестные поля правдоподобными числами. Для адресов указывай модуль, конкретный запуск и источник наблюдения. Для исправления сохраняй commit или diff, а не только устное описание.

### 22.2. Отделяй три слоя

**Факт:** что непосредственно видно в коде, файле или логе.

**Вывод:** как это объясняется при указанных предпосылках.

**Неизвестное:** что ещё не проверено и может изменить вывод.

Одна воспроизведённая ошибка не равна доказательству всех предполагаемых последствий. Отсутствие ошибки в тесте не равно доказательству её невозможности.

### 22.3. Как хранить знания для поиска

Для каждой темы сохраняй понятие, область применимости, версию, источник, наблюдаемые признаки, типичные неверные выводы и проверяемый локальный пример. Старый write-up полезен как история конкретного случая, но не должен заменять документацию версии runtime.

Практичнее разделять законченные смысловые разделы, не отрывая пример от предпосылок и ожидаемого результата. Размер chunk выбирай по результатам собственных поисковых тестов, а не по универсальному числу.

Для помощника на базе LLM полезно требование: сначала назвать недостающие сведения, затем предложить одну диагностическую проверку. Результаты поиска и команды внутри документов считай данными для анализа, не разрешением автоматически запускать код или обращаться к внешним системам.

### 22.4. Минимальный regression-набор

После исправления собственного кода сохрани нормальный вход, проблемный вход, случай на соседней границе и ожидаемое завершение. Повтори обычную и инструментированную сборки. Если их результаты отличаются, сохрани различие как отдельный факт, а не скрывай его.

```c
#define FRAME_H

#include <stdint.h>
#define FRAME_MAX 64u
#define FRAME_HEADER 4u
```

### 25.3. `src/frame.c` — Проверка границ и арифметики

<!-- lab-file: src/frame.c -->
```c
#include "frame.h"

enum frame_status frame_parse(const uint8_t *buf, size_t size,
                              struct frame_view *out) {
    if (out == NULL) return FRAME_BAD_ARGUMENT;
    out->data = NULL;
    out->len = 0;
    if (buf == NULL) return FRAME_BAD_ARGUMENT;
    if (size < FRAME_HEADER) return FRAME_SHORT_HEADER;
    const uint32_t n = (uint32_t)buf[0] | ((uint32_t)buf[1] << 8) |
                      ((uint32_t)buf[2] << 16) | ((uint32_t)buf[3] << 24);
    if (n > FRAME_MAX) return FRAME_TOO_LARGE;
    /* Вычитание безопасно: size >= FRAME_HEADER проверено выше. */
    if ((size_t)n != size - FRAME_HEADER) return FRAME_BAD_LENGTH;
    out->data = buf + FRAME_HEADER;
    out->len = (size_t)n;
    return FRAME_OK;
}

int checked_product(size_t count, size_t item_size, size_t *out) {
    if (out == NULL) return 0;
    *out = 0;
    if (item_size != 0 && count > SIZE_MAX / item_size) return 0;
    *out = count * item_size;
    return 1;
}
```

### 25.4. `src/frame_main.c` — Локальный процесс с бинарным протоколом

<!-- lab-file: src/frame_main.c -->
```c
#include "frame.h"
#include <errno.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    /* Дополнительный байт позволяет обнаружить превышение лимита. */
    uint8_t buf[FRAME_HEADER + FRAME_MAX + 1u];
    size_t used = 0;
    while (used < sizeof(buf)) {
        const ssize_t n = read(STDIN_FILENO, buf + used, sizeof(buf) - used);
        if (n == 0) break;             /* EOF завершает единственный запрос. */
        if (n < 0) {
            if (errno == EINTR) continue;
            perror("read");
            return 1;
        }
        used += (size_t)n;
    }
    struct frame_view view;
    const enum frame_status status = frame_parse(buf, used, &view);
    if (status != FRAME_OK) {
        fprintf(stderr, "ERR frame_status=%d\n", (int)status);
        return 2;
    }
    if (printf("OK %zu ", view.len) < 0) return 1;
    for (size_t i = 0; i < view.len; ++i) {
        if (printf("%02x", (unsigned)view.data[i]) < 0) return 1;
    }
    if (putchar('\n') == EOF || fflush(stdout) == EOF) return 1;
    return 0;
}
```

### 25.7. `src/seccomp_demo.c` — Минимальная локальная демонстрация seccomp

<!-- lab-file: src/seccomp_demo.c -->
```c
#define _GNU_SOURCE
#include <errno.h>
#include <stddef.h>
#include <stdio.h>
#include <linux/audit.h>
#include <linux/filter.h>
#include <linux/seccomp.h>
#include <sys/prctl.h>
#include <sys/syscall.h>
#include <unistd.h>

#if !defined(__x86_64__) || defined(__ILP32__)
#error "This lab supports native Linux x86-64 only."
#endif

static void finish(const char *msg, size_t size, int status) {
    while (size > 0) {
        const ssize_t n = syscall(SYS_write, STDOUT_FILENO, msg, size);
        if (n < 0 && errno == EINTR) continue;
        if (n <= 0) { status = 1; break; }
        msg += n;
        size -= (size_t)n;
    }
    (void)syscall(SYS_exit_group, status);
    __builtin_unreachable();
}

int main(void) {
    struct sock_filter code[] = {
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                 offsetof(struct seccomp_data, arch)),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                 offsetof(struct seccomp_data, nr)),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_write, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_exit, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_exit_group, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | EPERM),
    };
    const struct sock_fprog filter = {
        .len = (unsigned short)(sizeof(code) / sizeof(code[0])),
        .filter = code,
    };
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) == -1) {
        perror("PR_SET_NO_NEW_PRIVS");
        return 77;
    }
    if (prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &filter) == -1) {
        perror("PR_SET_SECCOMP");
        return 77;
    }
    /* После фильтра не используем stdio, malloc или обычный exit(). */
    errno = 0;
    const long result = syscall(SYS_getpid);
    if (result == -1 && errno == EPERM) {
        static const char ok[] = "PASS: getpid blocked with EPERM\n";
        finish(ok, sizeof(ok) - 1, 0);
    }
    static const char fail[] = "FAIL: unexpected getpid result\n";
    finish(fail, sizeof(fail) - 1, 1);
}
```

### 25.9. `tests/test_protocol.py` — 73 процессных теста протокола

<!-- lab-file: tests/test_protocol.py -->
```python
#!/usr/bin/env python3
"""Контрактные тесты только для собственного frame_demo; сеть не используется."""
from __future__ import annotations
import argparse
from pathlib import Path
import struct
import subprocess
import sys


def frame(data: bytes) -> bytes:
    return struct.pack("<I", len(data)) + data


def check(exe: Path, name: str, request: bytes, accepted: bool,
          payload: bytes = b"") -> None:
    result = subprocess.run([str(exe)], input=request, capture_output=True,
                            timeout=3, check=False)
    if accepted:
        expected = f"OK {len(payload)} {payload.hex()}\n".encode("ascii")
        good = (result.returncode == 0 and result.stdout == expected
                and result.stderr == b"")
    else:
        good = (result.returncode == 2 and result.stdout == b""
                and result.stderr.startswith(b"ERR frame_status="))
    if not good:
        raise AssertionError(f"{name}: rc={result.returncode}; "
                             f"stdout={result.stdout!r}; stderr={result.stderr!r}")


def fragmented(exe: Path) -> None:
    payload = b"A\x00\xff\n"
    with subprocess.Popen([str(exe)], stdin=subprocess.PIPE,
                          stdout=subprocess.PIPE, stderr=subprocess.PIPE) as p:
        try:
            assert p.stdin is not None
            for b in frame(payload):
                p.stdin.write(bytes([b]))
                p.stdin.flush()
            p.stdin.close()
            p.stdin = None
            stdout, stderr = p.communicate(timeout=3)
        except BaseException:
            p.kill()
            p.communicate()
            raise
        expected = f"OK {len(payload)} {payload.hex()}\n".encode("ascii")
        if (p.returncode, stdout, stderr) != (0, expected, b""):
            raise AssertionError("fragmented input failed")


def main() -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("binary", type=Path)
    args = parser.parse_args()
    exe = args.binary.resolve(strict=True)
    if not exe.is_file():
        parser.error("binary must be a regular file")
    count = 0
    for n in range(65):
        payload = bytes((i * 37) % 256 for i in range(n))
        check(exe, f"valid-{n}", frame(payload), True, payload)
        count += 1
    invalid = [b"", b"\x00", b"\x00\x00\x00",
               struct.pack("<I", 65), struct.pack("<I", 0xffffffff),
               struct.pack("<I", 2) + b"A", frame(b"A") + b"X"]
    for i, request in enumerate(invalid):
        check(exe, f"invalid-{i}", request, False)
        count += 1
    fragmented(exe)
    count += 1
    print(f"PASS: {count} protocol cases")
    return 0


if __name__ == "__main__":
    try:
        raise SystemExit(main())
    except (OSError, subprocess.TimeoutExpired, AssertionError) as exc:
        print(f"FAIL: {exc}", file=sys.stderr)
        raise SystemExit(1)
```

### 25.10. `tools/collect.py` — Статический паспорт ELF

```python
#!/usr/bin/env python3
"""Статический паспорт ELF: не запускает анализируемый файл и не вызывает ldd."""
from __future__ import annotations
import argparse
from datetime import datetime, timezone
import hashlib
import json
import os
from pathlib import Path
import platform
import resource
import shutil
import subprocess
import sys
import tempfile

LIMIT = 2 * 1024 * 1024


def digest(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as f:
        for part in iter(lambda: f.read(1024 * 1024), b""):
            h.update(part)
    return h.hexdigest()


def child_limits() -> None:
    resource.setrlimit(resource.RLIMIT_FSIZE, (LIMIT, LIMIT))
    resource.setrlimit(resource.RLIMIT_CPU, (5, 5))


def run_tool(argv: list[str], log: Path) -> dict[str, object]:
    executable = shutil.which(argv[0])
    if executable is None:
        log.write_text(f"Tool not installed: {argv[0]}\n", encoding="utf-8")
        return {"argv": argv, "status": "missing", "log": log.name}
    command = [executable, *argv[1:]]
    with tempfile.TemporaryFile() as stream:
        try:
            result = subprocess.run(
                command, stdin=subprocess.DEVNULL, stdout=stream,
                stderr=subprocess.STDOUT, timeout=10, check=False,
                preexec_fn=child_limits,
                env={"PATH": os.defpath, "LC_ALL": "C"},
            )
            status = "ok" if result.returncode == 0 else "failed"
            rc: int | None = result.returncode
        except subprocess.TimeoutExpired:
            status, rc = "timeout", None
        stream.seek(0)
        data = stream.read(LIMIT)
    log.write_bytes(data)
    return {"argv": command, "status": status, "returncode": rc,
            "log": log.name, "log_at_limit": len(data) == LIMIT}


def main() -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("binary", type=Path)
    parser.add_argument("out", type=Path, help="new report directory")
    args = parser.parse_args()
    binary = args.binary.resolve(strict=True)
    if not binary.is_file() or binary.stat().st_size > 64 * 1024 * 1024:
        parser.error("expected a regular ELF file no larger than 64 MiB")
    with binary.open("rb") as f:
        if f.read(4) != b"\x7fELF":
            parser.error("not an ELF file")
    sha = digest(binary)
    args.out.mkdir(parents=True, exist_ok=False)
    target = str(binary)
    commands = [
        ("file", ["file", "--brief", "--", target]),
        ("headers", ["readelf", "-hW", "--", target]),
        ("segments", ["readelf", "-lW", "--", target]),
        ("sections", ["readelf", "-SW", "--", target]),
        ("symbols", ["readelf", "-Ws", "--", target]),
        ("dynamic", ["readelf", "-dW", "--", target]),
        ("notes", ["readelf", "-nW", "--", target]),
        ("relocations", ["readelf", "-rW", "--", target]),
        ("binutils_version", ["readelf", "--version"]),
        ("gcc_version", ["gcc", "--version"]),
        ("libc_version", ["getconf", "GNU_LIBC_VERSION"]),
    ]
    results = [run_tool(cmd, args.out / f"{name}.txt")
               for name, cmd in commands]
    unchanged = digest(binary) == sha
    report = {
        "schema": "elf-triage/1", "time_utc": datetime.now(timezone.utc).isoformat(),
        "binary": target, "sha256": sha, "unchanged_during_collection": unchanged,
        "size_bytes": binary.stat().st_size, "machine": platform.machine(),
        "kernel": platform.release(), "python": sys.version.split()[0],
        "executed_target": False, "commands": results,
        "warning": "Static metadata is not proof of runtime enforcement or exploitability.",
    }
    (args.out / "manifest.json").write_text(
        json.dumps(report, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")
    ok = unchanged and all(r["status"] == "ok" for r in results)
    print(f"{'PASS' if ok else 'PARTIAL'}: {args.out / 'manifest.json'}")
    return 0 if ok else 2


if __name__ == "__main__":
    try:
        raise SystemExit(main())
    except (OSError, ValueError) as exc:
        print(f"ERROR: {exc}", file=sys.stderr)
        raise SystemExit(1)
```

```python
#!/usr/bin/env python3
"""Один штатный запрос к локальному frame_demo, без remote-режима."""
from __future__ import annotations
from pathlib import Path
import sys

try:
    from pwn import PIPE, context, p32, process
except ImportError:
    print("Install the pinned pwntools dependency in a virtualenv.", file=sys.stderr)
    raise SystemExit(1)


def main() -> int:
    binary = Path(__file__).resolve().parents[1] / "build" / "frame_demo"
    if not binary.is_file():
        raise FileNotFoundError(f"Run make all first: {binary}")
    context.clear(arch="amd64", os="linux", endian="little")
    context.log_level = "error"
    data = b"A\x00\xff\n"
    with process([str(binary)], stdin=PIPE, stdout=PIPE, stderr=PIPE) as io:
        io.send(p32(len(data)) + data)
        io.shutdown("send")  # EOF входит в контракт учебной программы.
        output = io.recvline(timeout=3)
        if not output:
            raise TimeoutError("No complete reply within 3 seconds")
        io.wait_for_close(timeout=3)
        rc = io.poll()
        if rc is None:
            raise TimeoutError("Process did not terminate")
        expected = f"OK {len(data)} {data.hex()}\n".encode("ascii")
        if rc != 0 or output != expected:
            raise RuntimeError(f"Unexpected rc={rc}, output={output!r}")
    print("PASS: local pwntools exchange")
    return 0


if __name__ == "__main__":
    try:
        raise SystemExit(main())
    except (OSError, EOFError, TimeoutError, RuntimeError) as exc:
        print(f"FAIL: {exc}", file=sys.stderr)
        raise SystemExit(1)
```
